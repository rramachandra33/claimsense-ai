ClaimSense AI – Design

Architecture and design reference · as built and deployed, November 2026 · decisions with dates are in DECISIONS.md; step-by-step flows in docs/workflows/

ClaimSense is a claims adjudication co-pilot for a motor insurer. Given a claim, it drafts a first decision (APPROVE, FLAG, ROUTE or DENY), the reasoning and the policy clauses it rests on, and writes it to the claim as a note. A licensed adjuster confirms or rejects every draft. All data is synthetic: the course's 20 claims, 15 policies, 74 documents and the 12-clause AutoSure policy manual.

1. Goals and principles

  1. Code decides what can be computed; the model judges and explains. Identity, access, policy dates, coverage purchased, deductibles, net payable, the total-loss ratio and the $25,000 senior threshold are worked out in code (facts.py). Four agents read the file, check coverage, assess risk and draft the decision, and the draft is checked against code before anything is written.
  2. Every decision is cited. A note must cite a clause that a search returned in that run. A clause the model invents, or one it never retrieved, never reaches a note: the draft is replaced by code's own (deterministic_fallback), and a made-up citation becomes a DENY for an adjuster to assess.
  3. A person decides. Every note is a draft pending confirmation; nothing is paid or closed automatically. Above $25,000 net payable only a senior adjuster may confirm (CLS-PAY-012).
  4. Agents hold no permissions of their own. Each agent gets a five-minute on-behalf-of (OBO) token for one user, one claim and one run, with only its own scopes. Agents can never list claims, write notes or mint tokens.
  5. One gate to the data. Everything (console, agents, batch) reaches PostgreSQL only through the data API, which checks the token, applies the access rule and writes the audit log on every call. The MCP server has no rules of its own.
  6. Nothing is lost when outcomes compete. Precedence is DENY > FLAG > ROUTE > APPROVE; code appends "Also needs:" and "Pending documentation:" so a FLAG still shows the specialist or the missing estimate.
  7. Claim data stays in AWS. Claude runs on Amazon Bedrock; the Agents SDK's own tracing (which uploads to OpenAI) is switched off; addresses, phone numbers and emails are removed from notes.
  8. Measured, not assumed. A 60-case evaluation runs in CI on every push (mock agents, free) and on Claude before a release (make golden: 60/60 on 2026-11-09).

2. System architecture

3. Components

3.1 Ops Console (platform/web)

Next.js (App Router, server components). Pages: Claims (the queue: only the claims the API lets this user read), Claim (claim, policy, documents, notes, Run assessment, Confirm/Reject), Document (OCR text), Policy manual (word search, or a clause id such as CLS-FRD-007 opens that clause) and Sign in.

  • The browser never holds a token in script. Sign-in is a server action: the console's server checks the password with Cognito (InitiateAuth, USER_PASSWORD_AUTH), asks the API who the user is (/api/v1/me) and keeps only the access token in an httpOnly cookie.
  • Every page calls the data API with that token; the console has no access rules of its own, so a list or a claim it shows is exactly what the API allows.
  • Run assessment posts to the runner. On a claim the claims system has already decided it first asks "It is already approved. Rerun it?" (a second opinion).
  • Sign-out clears the cookie and redirects with a relative address, so it works on any host name.

3.2 Runner and AgentCore (agent/src/claimsense_agent/runner.py)

A small FastAPI service. POST /runs takes a claim id with the adjuster's token. It also speaks the AgentCore Runtime contract (GET /ping, POST /invocations with the token in the body, because SigV4 uses the Authorization header). On EC2, when CLAIMSENSE_AGENTCORE_RUNTIME_ARN is set, /runs forwards the run to AgentCore with the instance's AWS credentials; on AgentCore the same image runs the pipeline. The runner has no secrets and no access rules: it passes the adjuster's token on.

A DENY code has no reason for becomes a FLAG that keeps the agents' reason (they may have seen an exclusion code cannot check).

3.4 Agents (agent/src/claimsense_agent/agents)

OpenAI Agents SDK with Claude on Bedrock through LiteLLM (bedrock.py); mock.py has the same four functions and typed outputs without a model, for tests, CI and free local runs. Each agent has at most 15 turns and 2,000 output tokens; LiteLLM retries transient Bedrock errors three times.

AgentModelOBO scopesOutput
ReaderHaiku 4.5claim:read, documents:readsummary, documents read and unreadable, findings
CoverageSonnet 4.5claim:read, policy:read, clauses:searchcovered (yes / no / cannot tell), reasoning, cited clauses
RiskHaiku 4.5claim:read, documents:read, clauses:searchrefer to SIU, indicators, cited clauses (≤3 searches)
DrafterSonnet 4.5claim:readoutcome, summary, cited clauses, deny reason

Coverage and risk citations that no search returned are dropped before the drafter sees them, so the drafter is never offered an unretrieved clause.

3.5 MCP server and registry (mcp_server/)

MCP over streamable HTTP at /mcp, with five read-only tools: get_claim, get_policy, list_documents, get_document and search_clauses. Each tool makes one call to the data API with the calling agent's OBO token and returns the answer unchanged. There is no tool to list claims or write notes. The same service hosts a registry at /registry/v0/servers (the MCP registry API shape); agents look up the server's URL there. It runs on Lambda because AgentCore could not reach it on the EC2 instance.

3.8 Policy manual and the clause guardrail

The manual's clauses are loaded by platform/db/seed. A guardrail (guardrail.py) checks every clause for injected instructions: a clean clause goes to claimsense.clause_index (full-text search, PostgreSQL tsvector with a GIN index); a suspicious one goes to claimsense.clause_quarantine with the pattern that matched, and can never be returned by a search. The planted chunk CLS-ADM-013 is quarantined; all 12 real clauses are indexed. Search ranks clauses with ts_rank over the query's words (any of them), and each search an agent makes is logged in claimsense.retrieval_log under its run, which is what the citation check reads.

Changes after the first release are dated migrations in platform/db/migrations/ (reviews and claim status, 2026-11-04; batch assessment, 2026-11-05). Note ids are one sequence across all claims.

3.10 Batch assessment (batch/)

EventBridge Scheduler calls Lambda claimsense-batch every 4 hours (deployed, schedule paused). It signs a short-lived token for the claimsense-batch account, asks the API for open claims never assessed or whose documents changed (a fingerprint of the documents is stored on each assessment), and runs them on AgentCore, three at a time, at most 25 a batch and $5 a day. A failed claim does not stop the batch and is not retried (the next batch picks it up). Notes are drafts for the assigned adjuster, author claimsense-batch.

3.11 Privacy and safety

  • Prompt injection: injected clauses are quarantined at load; document text and claim text are data to the agents, and whatever an agent concludes still passes the draft check (evaluation family attack, 9 cases).
  • Least privilege for agents: per-agent scopes, one claim, one run, five minutes; a token used on another claim, outside its scopes, to list claims, to write a note or after it expires is refused (family token).
  • Redaction (redact.py): street addresses, phone numbers and emails are removed from every note before it is written; only the last six characters of a VIN appear.
  • Audit: every API call, allowed or refused, with the user, the acting agent and the reason (the reason is never returned to the caller).
  • Idempotency: a retried note write with the same key returns the stored note; the same key with a different body is refused.
  • Secrets: the token secret and database password are generated on the instance and copied into the Lambdas' encrypted environment by the deploy scripts; never in git.

3.12 Observability

Each run is traced as spans (code facts, rule clauses, each agent, check draft, write note) with OpenTelemetry to CloudWatch (Transaction Search); the same trace prints in the terminal locally. Metrics in namespace ClaimSense: Runs, RunDurationMs, Failures, Resolutions (a run that writes a note), Fallbacks, AgentFailures, Decisions by outcome, InputTokens, OutputTokens, RunCostUsd, and EvalPassRate/EvalCostUsd for evaluation runs. Dashboards: Experience, Economics, Quality; alarms ClaimSense-SlowRuns and ClaimSense-BadRuns. Cost per run is computed from the token counts (pricing.py) and stored on the assessment.

3.13 Build and deploy

GitHub Actions on every push: database and course data, seed and guardrail tests, data API tests, MCP tests, pipeline tests, batch tests, then the evaluation gate (60 cases, mock agents, at least 90%). On main it builds the images, pushes them to ECR (tagged with the commit and latest) through GitHub OIDC (no stored AWS keys), and builds the runner for arm64 for AgentCore. Deployment is by script, in order: deploy/ec2, deploy/lambda, deploy/agentcore, deploy/observability, deploy/batch, deploy/cognito; each folder has its IAM policy and a README. DEPLOY_AND_TEST_ON_AWS.md walks through it from scratch.

5. Testing strategy

  • Unit and integration: data API 105 (access rule, Cognito tokens, OBO scopes, notes and reviews, the batch account, rate limit, Lambda handler), MCP server 9 (over HTTP), pipeline 75 + 1 opt-in Claude test, batch 5, seed and guardrail 4. All run in CI against a real PostgreSQL.
  • Evaluation (evals/cases.json, 60 cases): baseline 20 (every course claim as filed), variation 22 (one fact changed: a date, a threshold, cover, a document), attack 9 (injected instructions, fake or unretrieved clauses, personal details), access 4 and token 5. Cases that change a claim run on a temporary copy (CLM-9000-xxxx) that is removed afterwards. Each case checks the outcome, citations, that no other claim was read, and that no personal details reached the note.
  • CI gate: the 60 cases with mock agents, at least 90% (60/60 today), free, about a minute.
  • Release gate: make golden, the 60 cases on Claude. 2026-11-09: 56/60 in the full run, then 60/60 after a fix to the harness (temporary copies kept the original claim's ids in their document text); $4.25 in all. Report: docs/ClaimSense-AI-Golden-Run-2026-11-09.pdf.
  • On AWS: DEPLOY_AND_TEST_ON_AWS.md §4 tests every feature by hand: Cognito sign-in and refusals, both APIs, AgentCore, dashboards and alarms, the batch.

Measured: a run on Claude takes about 22 s and $0.07 (evaluation average, 1.6 million input tokens for 60 cases); through the console on AWS 30–60 s. Mock run: under a second.

6. Limits and next steps for production

  • HTTPS in front of the console, then the Secure cookie, Cognito's hosted page and MFA.
  • Shorter access tokens with refresh, so sign-out takes effect quickly.
  • Managed PostgreSQL (RDS) with backups; secrets in Secrets Manager or Parameter Store.
  • Row-level security in PostgreSQL as a second line behind can_read_claim.
  • The fraud threshold (0.70) is provisional: the manual gives no number.
  • Alarm notifications (SNS), log retention, reserved concurrency on the Lambdas.
